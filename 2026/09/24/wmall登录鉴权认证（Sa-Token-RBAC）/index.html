wmall 系统 Sa-Token + RBAC 鉴权体系深度分析

一、整体架构概览

本系统采用 Sa-Token（轻量级权限认证框架）+ 经典 RBAC（基于角色的访问控制）五表模型 的组合方案。核心设计思想是：登录态由 Sa-Token 管理，权限数据由数据库 RBAC 表提供，两者通过 StpInterface 接口桥接。

二、Sa-Token 配置层

1. 路由拦截器 SaTokenConfig.java

设计要点：

  • 注册 SaInterceptor，lambda 表达式 handle -> StpUtil.checkLogin() 表示默认所有请求必须先登录。
  • 白名单只放行登录、注册、健康检查等无需鉴权的接口。
  • 注解鉴权（@SaCheckPermission 等）由 SaInterceptor 内部自动识别并生效，无需额外配置。

2. application.yml 中的 Sa-Token 参数

is-share: false 是关键配置——同一用户在多个浏览器登录会得到不同 token，互不影响，避免踢下线问题。

四、登录/登出核心逻辑

UmsUserServiceImpl.login()

关键设计：

  • StpUtil.login(user.getId())：将用户 ID 作为 loginId 写入 Sa-Token 会话，框架自动生成随机 token 并存入 Redis。
  • StpUtil.getTokenValue()：获取当前 token 字符串返回给前端，前端后续请求携带 Authorization: Bearer xxx。
  • 密码使用 BCrypt 哈希存储（BCrypt.hashpw / BCrypt.checkpw），自带盐值，防彩虹表。
  • 登录失败锁定：连续 5 次密码错误，Redis key auth:login:fail:{username} 锁定 15 分钟（AuthConstants.LOCK_SECONDS = 900），防暴力破解。

七、RBAC 表结构详解

共 6 张表（5 张 RBAC 核心表 + 1 张登录日志表）：

1. ums_user 用户表

字段 类型 说明
id BIGINT PK 主键
username VARCHAR(50) UK 登录用户名，唯一
password VARCHAR(100) BCrypt 密文
nickname VARCHAR(50) 昵称
phone VARCHAR(20) 手机号（预留）
avatar VARCHAR(255) 头像地址
status TINYINT 1 正常 / 0 禁用
balance DECIMAL 账户余额（余额支付用）
deleted TINYINT 逻辑删除

2. ums_role 角色表

字段 类型 说明
id BIGINT PK 主键
role_code VARCHAR(50) UK 角色编码（admin/user），Sa-Token 鉴权用
role_name VARCHAR(50) 角色名称（展示用）
status TINYINT 1 正常 / 0 停用

3. ums_menu 菜单/权限表

字段 类型 说明
id BIGINT PK 主键
parent_id BIGINT 父级 ID，0 为根
menu_name VARCHAR(50) 菜单/权限名称
menu_type TINYINT 1 目录 / 2 菜单 / 3 按钮权限
perm_key VARCHAR(100) 权限标识（如 user:list），Sa-Token 鉴权核心字段
path VARCHAR(200) 前端路由
sort INT 排序
status TINYINT 1 正常 / 0 停用

menu_type=3 且 perm_key 非空的记录才是真正参与后端鉴权的”按钮权限”；目录和菜单主要用于前端菜单树渲染。

4. ums_user_role 用户-角色关联表

字段 类型 说明
user_id BIGINT 用户 ID
role_id BIGINT 角色 ID

联合主键 (user_id, role_id)，支持一个用户拥有多个角色。

5. ums_role_menu 角色-菜单关联表

字段 类型 说明
role_id BIGINT 角色 ID
menu_id BIGINT 菜单/权限 ID

联合主键 (role_id, menu_id)，支持一个角色拥有多个权限。

6. ums_login_log 登录日志表

记录登录/登出行为，包含用户 ID、用户名、IP、成功/失败状态、说明信息，用于安全审计。

九、为什么这么设计？

设计决策 原因
Sa-Token 而非 Spring Security Sa-Token 上手简单、API 直观（StpUtil.login()），无需复杂配置，适合中小型电商项目快速交付
StpInterface 桥接而非自定义拦截器 Sa-Token 原生支持 StpInterface 扩展，只需实现两个方法即可对接任意数据源，框架自动处理注解鉴权，减少样板代码
权限存数据库而非写死 权限可动态配置，管理员通过后台即可调整角色-菜单关系，无需改代码重启
perm_key 字符串标识而非数字 ID 可读性强，@SaCheckPermission("order:ship") 一目了然，便于前后端约定
is-share: false 多端登录互不踢下线，用户体验好
Redis 登录失败计数 无状态、可跨实例共享，防暴力破解不依赖本地内存
BCrypt 密码 自带盐值、慢哈希，抗彩虹表和暴力破解
逻辑删除 + status 双字段 deleted 防误删可恢复，status 用于临时禁用账号

十、完整调用链总结

  1. 用户登录 → AuthController.login() → UmsUserServiceImpl.login() → StpUtil.login(userId) → Sa-Token 在 Redis 存 token → userId 映射 → 返回 token
  2. 前端请求携带 Authorization: Bearer {token} → SaInterceptor 解析 token → StpUtil.checkLogin() 校验登录态
  3. 接口上的 @SaCheckPermission("xxx") 触发 → Sa-Token 回调 StpInterfaceImpl.getPermissionList(loginId) → 执行 SQL 查 ums_menu.perm_key → 比对权限
  4. 通过则执行业务，不通过抛 NotPermissionException → GlobalExceptionHandler 返回 403

这套方案实现了**登录认证、权限授权、异常处理、安全加固（锁定/BCrypt/日志）**的完整闭环，代码简洁且生产可用。
