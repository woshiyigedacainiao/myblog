wmall秒杀流程详解

发表于 2026-09-24

现在我已经掌握了整个秒杀流程的核心代码。让我整理一下完整的秒杀流程，包括：

  1. 活动管理（后台）：创建、上线、下线
  2. 前台抢购流程
  3. 结果查询
  4. 订单取消回补

让我整理出完整的流程图和说明。

核心文件：

  • SeckillController.java - 前台接口
  • AdminSeckillController.java - 后台管理接口
  • SeckillOrderServiceImpl.java - 秒杀下单主流程
  • SeckillStockServiceImpl.java - Redis 库存扣减（Lua）
  • SeckillTxServiceImpl.java - 事务内 DB 扣减 + 下单
  • SeckillActivityServiceImpl.java - 活动管理
  • seckill_deduct.lua - 预扣库存 Lua
  • seckill_return.lua - 回补库存 Lua
  • SmsSeckillActivityMapper.xml - DB 库存扣减 SQL

整个流程涉及的技术：

  • Redis + Lua 脚本（原子预扣库存 + 限购）
  • MySQL 条件更新（DB 层防超卖）
  • Spring 事务（@Transactional）
  • 事务同步器（TransactionSynchronization，事务提交后发通知）
  • 幂等（requestId）
  • Sa-Token 鉴权

解决的问题：

  1. 超卖问题（Redis Lua + DB 条件更新双保险）
  2. 超限购问题（Redis Hash 记录用户已购数量）
  3. 高并发性能问题（Redis 预扣，DB 兜底）
  4. 重复提交问题（requestId 幂等）
  5. 数据一致性问题（Redis 预扣成功但 DB 失败时回补 Redis）
  6. 订单取消后库存释放问题（DB + Redis 双向回补）
    现在我已经完整掌握了秒杀模块的所有核心代码，下面给你梳理完整的秒杀流程。

秒杀完整流程

整个秒杀体系分为 后台活动管理 → 前台抢购 → 结果查询 → 取消回补 四个阶段。

一、活动管理阶段（后台）

入口：AdminSeckillController.java

操作 方法 关键逻辑
创建活动 create() 校验时间、SKU 有效性，DB 插入，初始 availableStock = totalStock，状态=下线
编辑活动 update() 上线活动禁止编辑
上线活动 online() ① 状态改上线 ② 以 DB 剩余库存初始化 Redis seckill:stock:{id} ③ 清空上一轮 bought/joined key
下线活动 offline() 状态改下线，删除 Redis 三个 key

关键点：上线时把库存从 DB 同步到 Redis，Redis 是抢购时的第一道闸门。

二、前台抢购阶段（核心）

入口：SeckillController.execute() → SeckillOrderServiceImpl.execute()

完整执行链路如下：

第 ⑥ 步：Redis Lua 原子预扣（seckill_deduct.lua）

为什么用 Lua？ 因为 GET → 判断 → DECRBY 不是原子的，高并发下会超卖。Lua 脚本在 Redis 单线程中执行，保证整个判断+扣减是原子的。

第 ⑧ 步：DB 层二次扣减（SeckillTxServiceImpl.createSeckillOrder）

这是 第二道防超卖闸门。即使 Redis 出问题，DB 条件更新也不会让库存变负数。整个方法加了 @Transactional，扣库存 + 插订单 + 插订单项要么全成功要么全回滚。

异常回滚机制

如果第 ⑧ 步 DB 落库失败（抛异常），会调用 rollbackRedis() → seckill_return.lua 把刚才 Redis 预扣的库存和限购记录回补回去，保证 Redis 与 DB 一致。

三、结果查询阶段

SeckillOrderServiceImpl.result()：根据 activityId + userId 查最新订单，返回秒杀是否成功、订单号、状态、金额等。

四、订单取消回补阶段

OrderServiceImpl.restoreSeckillStock()：用户取消秒杀订单时，DB 库存回补 + Redis 库存与限购记录回补，双向保持一致。

用到了什么技术？解决了什么问题？

技术手段 解决的问题
Redis + Lua 脚本 高并发下原子性扣库存，避免 GET-判断-DECRBY 的竞态导致超卖
Redis Hash（seckill:bought） 记录每个用户已购数量，解决超限购问题（一人只能买 N 件）
DB 条件更新（WHERE available_stock >= quantity） 第二道防超卖闸门，Redis 挂了也不会卖超
Spring @Transactional DB 扣库存 + 生成订单原子性，防止扣了库存没订单或有订单没扣库存
requestId 幂等校验 防止用户重复点击/网络重试导致重复下单
Redis 预扣 + DB 兜底 + 失败回补 解决高并发性能（Redis 扛流量）与数据一致性（DB 为准，失败回补 Redis）
TransactionSynchronization.afterCommit 事务提交成功后才发站内信，避免通知失败导致订单回滚
Redis Set（seckill:joined） 去重统计参与人数，用于后台转化率分析

一句话总结架构思路

Redis 扛流量（Lua 原子预扣+限购），DB 保数据（条件更新防超卖），事务保一致，幂等防重复，回补保闭环。

这是一个经典的「Redis 预扣 + DB 兜底」双保险秒杀方案，在保证不超卖、不超限购的前提下，用 Redis 承接了绝大部分高并发请求，DB 只处理真正抢到的少量订单。
