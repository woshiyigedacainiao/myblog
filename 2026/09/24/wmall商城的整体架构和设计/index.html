从 0 写一个高并发电商秒杀系统：Spring Boot + Redis + RabbitMQ 架构实战

一、项目背景与技术选型

这是一个前后端分离的单体电商系统，除了常规的商品、订单、支付，还包含一套完整的秒杀模块。单体而非微服务，是因为课程/中小项目场景下，单体在开发效率、部署成本、调试难度上都更优，而高并发能力通过 Redis + MQ + 乐观锁在单体内部解决。

层次 技术 版本
基础框架 Spring Boot / JDK 4.0.8 / 17
ORM MyBatis-Plus 3.5.17
认证授权 Sa-Token 1.46.0
缓存/库存 Redis 7.4（Lua 脚本）
消息队列 RabbitMQ 4.0（手动 ACK + 死信）
数据库 MySQL 8.0
工具 Hutool 5.8.44（BCrypt / 雪花 ID / JSON）

四、核心业务一：普通下单的异步可靠链路

这是整个系统最复杂的部分。难点在于：下单接口要快（不能同步等数据库扣库存），但库存、订单、消息三者又必须最终一致，消息绝不能丢。

采用「Redis 预扣 + 本地消息表 + MQ 异步确认 + 定时补偿」方案。

4.1 阶段一：Redis Lua 预扣库存

下单第一步不碰 MySQL，先在 Redis 扣。为什么用 Lua？因为”判断库存够不够”和”扣减”必须是一个原子操作，否则高并发下两个线程都读到充足库存、都扣，就超卖了。Redis 单线程执行 Lua，整个脚本天然原子：

4.2 阶段二：本地消息表 + afterCommit 发送

订单、订单项、本地消息写在同一个数据库事务里。关键设计是：消息不能在事务内发，而要等事务真正提交成功后再发。用 Spring 的事务同步回调实现：

为什么不用 @Async 或直接在方法末尾发？因为那时事务可能还没提交，一旦发了 MQ 但事务回滚，消费者就会读到一个不存在的订单。afterCommit 从机制上杜绝了这个问题。

注意：这个事务方法放在独立的 OrderTxServiceImpl 中，而不是 OrderServiceImpl 内部方法互调。Spring 声明式事务靠代理对象生效，同类内部调用会绕过代理导致事务失效，这是非常经典的坑。

4.4 阶段四：消费者幂等确认 + 手动 ACK

消费者拿到消息后做三件事：消费幂等 → 锁 DB 库存 → CAS 改订单状态，全程手动 ACK：

幂等做了三重防护：订单已取消（消息迟到）跳过、订单已非待确认（重复投递）跳过、消费日志 msg_id 唯一索引兜底。然后锁库存、用条件更新把订单从”待确认”改为”待付款”：

消费失败的消息进入死信队列，由专门的死信消费者落库 oms_dead_letter 并打 ERROR 日志，方便人工排查，消息不会凭空消失。

4.5 阶段五：定时补偿

万一应用在 afterCommit 后宕机、消息没发出去怎么办？本地消息表里还有记录。定时任务每分钟扫描重投，指数退避，超过 5 次置失败并告警。至此整条链路消息不丢、消费不重、失败可追溯。

五、核心业务二：秒杀的双层防超卖

秒杀和普通下单的设计刻意不同：秒杀是同步下单、不走 MQ。因为秒杀是单活动单 SKU、库存独立、要求点击立即知道结果，多一层 MQ 只会增加延迟和复杂度。

八、兜底层：三个定时任务

用 @EnableScheduling + @Scheduled 做最终一致性的最后防线：

任务 频率 职责
超时订单取消 1 分钟 待确认超 2 分钟 / 待付款超 30 分钟 → CAS 取消并回补库存
本地消息补偿 1 分钟 扫待发送消息重投，指数退避，超 5 次置失败告警
库存对账修复 5 分钟 游标分页比对 DB 与 Redis，偏差以 DB 为准重置

每个订单/消息独立 try-catch，单条失败不影响整批；通知类操作通过 @Async 异步执行且只记日志，绝不阻塞交易主流程。

九、架构亮点与踩坑总结

三个最有技术含量的设计：

  1. 双层库存闸门：Redis Lua 负责高并发快速失败，DB 条件更新负责最终正确性，即使缓存异常也绝不超卖。
  2. 本地消息表 + afterCommit + confirm/return + 定时补偿：一套完整的分布式事务最终一致性方案，消息不丢、不重、可追溯。
  3. CAS 状态机：订单状态、余额、库存全部用带前置条件的 UPDATE，无锁化解决并发问题。

踩过的坑（供参考）：

  • Spring 的 @Transactional 同类内部调用失效 → 拆独立 TxService Bean。
  • 事务没提交就发 MQ → 用 TransactionSynchronization.afterCommit。
  • Sa-Token 的 sa-token-redis-jackson 强依赖 Jackson 2，与 Spring Boot 4 内置的 Jackson 3 冲突启动报 NoClassDefFoundError → 换成不绑定 Jackson 版本的 sa-token-redis-template。
  • Lua 扣减数量必须和下单数量严格一致，限购计数也要在同一脚本内完成，否则会出现”Redis 扣了但限购失效”的并发漏洞。
  • 分类筛选要包含子孙分类，否则点一级分类查不到挂在三级分类下的商品。

这套架构没有用任何”高大上”的组件，全部是 Spring Boot 生态最主流的技术，但把 缓存原子性、消息可靠性、数据库乐观并发 这三个分布式系统的核心问题在一个单体里完整落地了——这也是它适合作为技术博客和课程设计的原因：麻雀虽小，五脏俱全。
