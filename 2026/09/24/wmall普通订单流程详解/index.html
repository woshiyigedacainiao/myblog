wmall普通订单流程详解

发表于 2026-09-24

整体流程：

  1. 用户下单 → Redis 预扣库存 → 事务内写入订单+订单项+本地消息表 → 事务提交后发 MQ
  2. MQ 消费 → 锁 DB 库存 → 订单状态从 CONFIRMING → WAIT_PAY
  3. 用户支付 → 扣 DB 锁定库存 → 状态 WAIT_PAY → WAIT_SHIP
  4. 发货/收货/退款等后续流转

本地消息表的核心：

  • 事务内把消息写入 oms_local_message 表，保证订单和消息的原子性
  • 事务提交后（afterCommit）才发送 MQ
  • Publisher Confirm 回调维护消息状态
  • 定时任务扫描未成功投递的消息，指数退避重投
  • 超过最大重试次数置失败，人工介入

补偿任务：

  1. 本地消息补偿投递（每分钟）
  2. 超时订单取消（每分钟）
  3. DB/Redis 库存对账修复（每5分钟）

死信队列：消费失败的消息进死信队列，落库留痕告警。

消费幂等：oms_consume_log 表的 msg_id 唯一索引兜底。

正常购物完整流程

整个下单流程采用 「Redis 预扣 + MQ 异步确认 + 本地消息表兜底」 的架构，核心解决高并发下库存一致性和消息可靠性问题。

整体状态机

一、下单阶段（核心）

入口：OrderServiceImpl.createOrder()

为什么状态是「待确认」而不是直接「待付款」？

因为 Redis 预扣只是临时占用，真正的 DB 库存锁定要靠 MQ 异步完成。订单先进入 CONFIRMING 中间态，等 MQ 消费成功锁定 DB 库存后，才转为 WAIT_PAY。这样做的好处是 下单接口快速返回，DB 锁库存异步化，提升吞吐量。

二、MQ 消费阶段（异步锁库存）

入口：OrderCreateConsumer.onMessage() → OrderTxServiceImpl.confirmOrder()

消费端采用 手动 ACK，任何异常都 basicNack(requeue=false) 转入死信队列，不无限重试。

本地消息表实现详解

这是整个流程最核心的可靠性保障机制。

表结构（oms_local_message）

字段 说明
msg_id 消息唯一 ID（雪花算法）
exchange / routing_key MQ 路由信息
payload JSON 序列化的消息体
status 0 待发送 / 1 已投递 / 2 已消费 / 3 失败
retry_count / max_retry 已重试次数 / 最大重试次数
next_retry_time 下次可重试时间
remark 失败原因

核心机制：事务内写消息 + 事务后发消息

解决的问题：如果先发 MQ 再写库，MQ 发成功但 DB 回滚，消费者收到消息却找不到订单；如果先写库再发 MQ，DB 提交后发 MQ 时网络闪断，消息就丢了。本地消息表让 消息和订单在同一事务内持久化，保证「订单在，消息就在」。

补偿任务实现详解

OrderScheduleTasks 定义了三个定时任务：

任务 1：本地消息补偿投递（每分钟）

LocalMessageCompensateService.compensate()

指数退避策略：

退避公式：BASE_BACKOFF * 2^(min(retryCount-1, 4))，封顶 300 秒。

任务 2：超时订单取消（每分钟）

OrderServiceImpl.cancelTimeoutOrders()

这解决了 消息丢失后订单永远卡在 CONFIRMING 的问题——超时后直接取消并回补 Redis 库存。

任务 3：DB/Redis 库存对账（每 5 分钟）

StockService.batchCheck() + repairToDb()

这解决了 Redis 与 DB 库存最终一致性 问题——任何异常导致的偏差都会被定时对账修复。

死信队列兜底

消费失败的消息（库存不足、状态冲突等）通过 basicNack(requeue=false) 转入死信队列 order.dlx.queue，由 OrderDeadLetterConsumer 落库到 oms_dead_letter 表并 ERROR 告警，等待人工介入。

用到的技术及解决的问题

技术手段 解决的问题
本地消息表（oms_local_message） 解决「DB 事务与 MQ 发送的原子性」问题，保证消息至少投递一次
事务后发送（afterCommit） 避免消息先发但事务回滚导致的脏消息
Publisher Confirm + Return 回调 感知消息是否真正到达 broker，失败则标记待重试
定时补偿任务 + 指数退避 MQ 发送失败后的自动重投，避免消息永久丢失；退避防止 broker 压力过大
死信队列（DLX） 消费失败的消息集中留痕告警，避免无限重试阻塞队列
消费幂等日志（oms_consume_log，msg_id 唯一索引） MQ 重复投递时不会重复锁库存、重复改状态
Redis 预扣 + DB 锁库存两阶段 下单快速返回（Redis 扛量），DB 保证数据准确（最终一致性）
CAS 状态更新（WHERE status = from） 防止并发状态流转冲突（如同时支付和取消）
DB 条件扣库存（WHERE stock >= qty） 数据库层防超卖，Redis 挂了也不会卖超
超时订单取消任务 消息丢失/用户不付款时自动释放库存，避免库存长期占用
库存对账任务 定期修复 DB/Redis 偏差，保证最终一致

一句话总结

整个正常购物流程围绕 「最终一致性」 设计：用 本地消息表 保证 MQ 不丢，用 消费幂等 保证 MQ 不重，用 Redis 预扣+DB 锁定 两阶段保证库存准确，用 超时取消+对账任务 兜底异常场景。即使任何一个环节出问题，都有补偿机制把数据拉回一致状态。
