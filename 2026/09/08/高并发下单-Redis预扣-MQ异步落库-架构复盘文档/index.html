高并发下单 Redis预扣+MQ异步落库 架构完整复盘文档

一、基础业务流程

核心流程

用户下单 → Redis Lua 脚本校验库存 + 预扣库存

  1. Redis 库存不足：直接返回库存不足，下单失败

  2. Redis 预扣成功：发送 MQ 消息，消费者异步操作数据库，完成真实库存扣减、订单生成

架构核心目标

实现服务高可用，保证 Redis 缓存库存 与 DB 真实库存的最终数据一致性

二、架构核心风险点（六大核心问题）

该异步架构存在严重的数据不一致、服务异常风险，是整套方案重点解决的痛点：

  1. 库存泄露：Redis 预扣成功，服务突然宕机，MQ 消息未生成。最终 Redis 库存已扣减，但数据库无订单记录、真实库存未扣减，造成库存丢失。

  2. 消息丢失：MQ 消息丢失或消费者消费失败，数据库永久不扣减真实库存，Redis 预扣库存永久占用。

  3. 超卖问题：MQ 消息重复消费，导致数据库重复扣减库存，出现超卖。

  4. 库存锁死：Redis 预扣库存后，下游业务执行失败，未回滚 Redis 库存，导致库存永久锁定，用户无法正常下单。

  5. 服务不可用：Redis 宕机，整体下单链路直接瘫痪，无法承接请求。

  6. 超时库存占用：用户下单超时、放弃支付，预扣的临时库存未及时释放，导致库存资源浪费。

三、整体设计大原则

  1. 数据真值原则：数据库 DB 是库存唯一真值，Redis 仅作为临时预占缓存，不存储真实库存数据。

  2. 最终一致原则：Redis 所有库存数据，最终以数据库数据为准，支持全量重建、校正覆盖。

  3. 预扣回滚原则：Redis 临时预扣库存，若后续订单未正常落地，必须强制归还、释放库存。

四、分层完整解决方案

1. Redis 层：高可用 + Lua 原子预扣设计

（1）高可用部署规范

  • 禁止单机 Redis 部署，生产环境使用 Redis Cluster 集群 或 「主从 + 哨兵」架构，避免单点宕机导致下单服务瘫痪。

  • 开启 RDB+AOF 双重持久化，防止节点宕机导致内存预扣数据全部丢失。

（2）Lua 脚本原子性保障

所有库存校验、预扣操作必须通过 Lua 脚本完成，单脚本原子执行，禁止拆分多条命令，杜绝并发超卖。

Lua 返回值约定

  • 返回 0：商品库存不足，下单失败

  • 返回 1：库存预扣成功，同时记录预扣标识、绑定订单 ID、设置过期时间

Lua 核心伪代码

（3）核心注意点

  • 预扣记录默认设置 30 分钟过期时间，匹配下单支付超时规则。

  • Redis Key 过期仅为标记状态，不会自动归还库存，库存释放需要业务代码定时处理。

  • 严格区分缓存与真值：Redis 可随时根据 DB 数据全量重建，不依赖缓存数据。

2. 发送方链路：解决宕机丢消息、库存泄露

（1）错误流程（高危 Bug）

Redis Lua 预扣成功 → 直接发送 MQ

  • 风险：发送 MQ 前服务宕机，消息未生成，Redis 库存被扣、DB 无数据，造成永久库存泄露。

（2）标准正确流程

  1. Lua 脚本预扣库存成功；

  2. DB 事务兜底：同一事务中，插入「待确认订单记录」+「本地消息表（待发送状态）」，统一提交；

  3. 事务异常：数据库写入失败，立即执行 Lua 脚本回滚 Redis 库存，返回下单失败，不发送 MQ；

  4. 事务成功：提交后发送 MQ 消息，投递成功后更新本地消息表为「已发送」；

  5. 定时任务补偿：后台定时扫描本地消息表中「待发送」消息，自动重试投递，超过最大重试次数则标记失败并告警。

（3）MQ 投递辅助保障

  • RabbitMQ：开启 publisher-confirm 确认机制

  • Kafka：设置 acks=all

  • 注意：以上配置仅为辅助，无法替代本地消息表，不能单独保证消息可靠。

3. MQ Broker 层：高可用防丢失

  1. 集群多副本部署，消息开启持久化，Broker 重启不丢失消息；

  2. 配置死信队列 DLQ：多次消费失败的消息转入死信队列，人工排查，禁止无限重试阻塞业务队列；

  3. 实时监控：消息堆积、消费失败、消息延迟，异常立即告警；

  4. 边界说明：Broker 仅保证投递后的消息不丢失，无法解决业务未生成消息的宕机问题。

4. 消费方：幂等消费、防超卖、防丢失

消费者核心职责：异步消费消息，在数据库完成真实库存扣减、正式订单生成。

（1）核心配置

关闭 MQ 自动 ACK，全程使用手动 ACK机制：

  1. 接收消息，通过唯一 orderId 做幂等校验；

  2. 数据库执行业务：创建正式订单、扣减真实库存、更新订单状态；

  3. 业务执行成功，手动 ACK；执行异常，不 ACK，等待 MQ 重试。

（2）DB 级别强幂等（核心防超卖）

  • 订单表 orderId 设置唯一索引；

  • 重复消费时，插入订单会触发唯一索引冲突，直接 ACK 跳过，杜绝重复扣库存；

  • 禁止依赖 Redis 做幂等，Redis 宕机、清空会导致幂等失效。

（3）异常分类处理

  • 瞬时异常（网络抖动、DB 短暂宕机）：不 ACK，等待 MQ 自动重试；

  • 业务异常（商品下架、参数错误）：直接转入死信队列，告警人工处理。

（4）消息有序性

同一商品 ID 的消息路由至同一个 MQ 分区，避免消息乱序导致数据异常。

5. 两大兜底补偿机制（架构最后防线）

MQ 仅能处理「预扣成功、DB 已有记录」的场景，极端宕机场景必须依靠兜底任务。

兜底 1：预扣超时库存回收（解决库存锁死）

  • 场景：用户放弃下单、MQ 持续消费失败，待确认订单长期未完成，Redis 库存永久占用；

  • 方案：订单设置 30 分钟超时时间，定时任务扫描 DB 中待确认 + 已超时的订单；

  • 执行逻辑：修改订单为「已取消」，调用 Lua 脚本归还 Redis 预扣库存，释放资源。

兜底 2：全局库存数据校正（最高级别兜底）

  • 场景：极端宕机（预扣成功、未写入 DB 即宕机），库存泄露，超时任务无法识别；

  • 方案：每 5 分钟执行一次全局校正任务；

  • 执行逻辑：读取 DB 真实库存、Redis 缓存库存，数据比对；以 DB 真值为准，强制修正 Redis 库存，异常数据触发告警记录。

五、完整全流程时序图

  1. 用户发起下单请求；

  2. Redis Lua 原子校验库存、预扣库存：库存不足直接失败，预扣成功继续执行；

  3. 开启 DB 事务：插入待确认订单、写入本地消息表；事务失败则回滚 Redis 库存，终止下单；

  4. DB 事务提交成功，发送 MQ 消息，定时任务兜底重试投递；

  5. MQ 消费者手动消费，幂等校验后落库订单、扣减真实库存，手动 ACK；

  6. 定时任务 A：扫描超时待确认订单，取消订单并归还 Redis 库存；

  7. 定时任务 B：全局比对 DB 与 Redis 库存，修复数据偏差、告警异常。

六、核心避坑清单

✅ 正确规范

  1. Redis 集群高可用 + Lua 原子预扣，区分缓存与真值；

  2. 预扣成功先落 DB、再发 MQ，异常必回滚缓存库存；

  3. MQ 集群持久化 + 死信队列 + 监控告警；

  4. 消费端手动 ACK + DB 唯一索引幂等，杜绝超卖；

  5. 超时回收任务，防止库存永久锁死；

  6. 全局数据校正，兜底所有极端异常。

❌ 致命错误

  1. 预扣成功直接发 MQ，无 DB 落地，宕机库存泄露；

  2. 消费端开启自动 ACK，DB 写入失败但消息已消费，数据丢失；

  3. 无幂等机制，重复消费导致库存超卖；

  4. 无超时归还逻辑，库存长期锁定；

  5. 将 Redis 缓存库存当作真实库存，无法修复数据错乱。

七、架构方案短板 & 选型对比

（1）方案短板

  1. 属于最终一致性架构，下单仅返回「下单中」，无法同步返回下单成功；

  2. 前端需要轮询或消息通知，查询订单最终状态，用户体验有延迟。

（2）架构选型取舍

  1. Redis 预扣 + MQ 异步落库：适配高并发秒杀、大流量下单场景，牺牲实时性，换高性能、高吞吐；

  2. 先 DB 扣库存 + 后更新缓存：适配普通下单、需要实时返回下单成功的业务，吞吐较低，实时一致性更强。
