一、模拟支付（payOrder）

1.1 涉及技术

技术点 用途
@Transactional 多表操作（扣余额 + 改订单状态）保证事务一致性

1.2 踩坑记录

🔴 坑1：余额比较用 > 漏掉了刚好相等的情况

原理：compareTo 返回值：> 0 大于，== 0 等于，< 0 小于。用 >= 0 才包含”刚好够”。

🔴 坑2：Controller 的 @PathVariable 漏写

🔴 坑3：订单状态判断缺少 else 分支

如果订单已支付或已取消，没有明确提示，用户只看到”支付失败”，不知道为什么。

二、RabbitMQ 连接报错

2.1 报错信息

2.2 排查过程

步骤 命令 结果
1. 测试端口是否通 Test-NetConnection -ComputerName 192.168.100.128 -Port 5672 TcpTestSucceeded: True ✅
2. 检查 RabbitMQ 管理面板 浏览器打开 192.168.100.128:15672 连接正常，用户 wzc 在线 ✅
3. 检查 YAML 配置 查看 application.yaml 发现 rabbitmq 缩进错误 🔴

2.3 🔴 坑：YAML 缩进导致配置路径错误

原理：Spring Boot 读取 RabbitMQ 配置的路径是 spring.rabbitmq.*，不是 spring.data.rabbitmq.*。data 下面只放 redis、mongodb、elasticsearch 等数据存储。RabbitMQ 是消息中间件，和 data 平级。

教训：YAML 的缩进决定了配置的层级关系，一个空格缩进错误就会导致整个配置失效，而且不会报错，只是默默用默认值（localhost:5672）。

三、接口防刷拦截器（AOP + Redis）

3.1 涉及技术

技术点 用途

3.2 核心设计

3.3 踩坑记录

🔴 坑1：注解声明用 class 而不是 @interface

原理：Java 有4种元注解类型，自定义注解必须用 @interface 关键字。class 是普通类，不支持 default 语法。

🔴 坑2：AOP 切面被注入到 Controller

原理：AOP 的工作原理是 Spring 在运行时生成代理对象。当方法上有 @RepeatSubmit 注解时，Spring 自动在方法执行前调用 @Before 切面逻辑。你不需要（也不应该）手动注入切面类。

🔴 坑3：Boolean 空指针风险

原理：null.equals(x) 会抛 NullPointerException，但 Boolean.FALSE.equals(null) 只会返回 false。这是一个经典的 Java 防御性编程技巧。

🟡 坑4：异常提示信息语义不对

教训：不同的业务场景应该有不同的错误提示。”重复下单”是业务层的幂等校验，”请求过于频繁”是防护层的防刷拦截，两者语义不同。

4.3 AOP 核心注解速查

注解 含义 使用场景
@Before 方法执行前触发 参数校验、权限检查、防刷

五、踩坑 Checklist（开发时对照检查）

  • YAML 缩进是否正确？配置路径是否是 Spring Boot 标准路径？
  • BigDecimal 比较是否用了 compareTo 而不是 > < equals？
  • @PathVariable / @RequestParam 是否漏写？
  • Boolean 包装类型比较是否用了 Boolean.FALSE.equals(result) 防止 NPE？
  • 自定义注解是否用了 @interface 而不是 class？
  • AOP 切面是否被错误地注入到了 Controller？
  • 异常提示是否区分了不同业务场景的语义？
  • 多表操作是否加了 @Transactional？
  • 枚举存入数据库时是否用了 .getCode() 而不是枚举对象本身？
