📝 第 3 步：秒杀核心流程 - 问题与解决方案笔记

一、分布式锁 Key 设计

问题

锁的 key 应该设置成什么？用用户 ID 还是活动 ID？

分析

方案 Key 效果
全局锁 miaosha:lock 所有请求排队，不同活动也互斥 ❌ 性能差
用户锁 miaosha:lock:{用户ID} 同一用户互斥，但不同用户可以同时操作同一活动库存 ❌ 会超卖
活动锁 miaosha:lock:{活动ID} 同一活动内串行，不同活动并行 ✅ 推荐

项目解决方案

核心理解：锁要锁住的是共享资源（库存），而不是请求者（用户）。

分析

项目解决方案

关键点：Redis 执行 Lua 脚本是原子性的，整个脚本执行期间不会被其他命令打断。

踩坑记录

  • Lua 脚本每段之间必须有空格，否则拼接后 thenredis.call(...) 连在一起，Redis 无法解析
  • KEYS 参数要大写：KEYS[1] 而不是 keys[1]
  • 传入的 key 必须是库存 key（STOCK_KEY），不是锁 key

三、RabbitMQ 异步下单

问题 1：消息序列化不匹配

现象：生产者发送 OrderDto 对象，消费者反序列化时报错。

原因：rabbitTemplate.convertAndSend() 默认用 Java 序列化，消费者端期望 JSON。

项目解决方案：创建 RabbitMQConfig 配置类

配置后，生产者和消费者自动使用 JSON 格式，发送代码不需要改。

问题 2：手动 ACK 配置了但消费者没实现

现象：YAML 配置了 acknowledge-mode: manual，但消费者没有调用 basicAck。

后果：消息永远不会被确认 → RabbitMQ 重复投递 → 重复创建订单。

项目解决方案：消费者实现手动确认

核心 API 理解：

API 含义 参数
basicAck(tag, false) 确认消息 deliveryTag=消息编号, false=不批量
basicNack(tag, false, true) 拒绝消息 tag=编号, false=不批量, true=重新入队

类比理解：

  • 自动确认 = 快递放门口自动签收（可能货不对板）
  • 手动确认 = 先验货再签收（有问题可以拒收退回）

问题 3：YAML 配置层级错误

现象：management.health.rabbit.enabled: false 不生效，健康检查一直报错。

原因：把 management 嵌套在了 rabbitmq 下面。

项目解决方案：management 是顶级配置，必须顶格写

问题 4：重复下单检查有漏洞

现象：用 MySQL 查询检查重复下单，但订单是异步写入的，高并发下检查无效。

项目解决方案（待实现）：用 Redis Set 原子操作代替 MySQL 查询
