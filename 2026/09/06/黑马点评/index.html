📋 Redis解决库存超卖和一人一单的完整逻辑

一、核心问题

在高并发秒杀场景下，需要解决两个关键问题：

  1. 库存超卖：多个用户同时抢购，可能导致库存扣减为负数
  2. 一人一单：同一个用户不能重复购买同一张秒杀券

二、解决方案演进

从你的代码中可以看到两种方案：

方案1：基于数据库 + 分布式锁（注释掉的代码，第89-129行）

存在的问题：

  • ❌ 先查数据库再判断，高并发下有性能瓶颈
  • ❌ 每个用户都要加锁，串行执行，吞吐量低
  • ❌ 一人一单在数据库层面判断，仍然要访问数据库

方案2：基于Redis + Lua脚本（当前使用的方案，第60-85行） ✅

这是更优的解决方案，核心在于seckill.lua脚本。

五、核心要点

✅ 库存Key是预先创建的：在添加秒杀券时就初始化到Redis

✅ 订单Key是延迟创建的：第一个用户购买时才由 SADD 自动创建

✅ 这是Redis的优势：不需要手动判断Key是否存在，命令会自动处理

✅ 保证原子性：Lua脚本中判断和添加是原子操作，不会出错

这就是Set集合的创建逻辑！简单说就是：不用你管，Redis自己会创建 😊

三、SISMEMBER 命令详解

返回值规则：

  • 1 = 成员存在于Set中
  • 0 = 成员不存在（包括Key不存在的情况）

四、为什么这样设计是安全的？

安全性保证：

  1. ✅ Key不存在 = 用户没买过 → 允许购买
  2. ✅ Key存在但用户不在 = 其他用户买过，当前用户没买 → 允许购买
  3. ✅ Key存在且用户在 = 当前用户已买过 → 拒绝重复下单

五、对比：不同命令对不存在Key的处理

命令 Key不存在时的行为 是否创建Key
SISMEMBER key member 返回 0 ❌ 不创建
SADD key member 创建空Set，添加member ✅ 自动创建
GET key 返回 nil ❌ 不创建
SET key value 创建Key并设值 ✅ 自动创建
INCR key 创建Key并设为0，再+1 ✅ 自动创建

七、总结

对于你的问题 “第一个用户执行到 SISMEMBER 会怎样”：

  1. ✅ 不会报错：Redis容错性很好
  2. ✅ 返回 0：表示该用户不在Set中（因为Set还不存在）
  3. ✅ 继续执行：if(0) 为 false，不会进入 return 2
  4. ✅ 后续创建：执行到 SADD 时才真正创建Set
  5. ✅ 逻辑正确：完美实现”一人一单”的判断

这就是Redis设计的巧妙之处：查询类命令不创建Key，写入类命令自动创建Key，既安全又高效！🎯

🔟 捕获异常并处理 Pending 消息

  • 代码位置: VoucherOrderHandler.java:63-99

Pending 机制原理:

  • 当消息被读取但未ACK时，会进入 Pending List
  • ReadOffset.from("0"): 从 Pending List 的第一个消息开始读取
  • 确保异常情况下消息不会丢失，会被重新处理

🎯 核心设计要点

✅ 优势

  1. 高性能: 用户请求只需执行Lua脚本（内存操作），立即返回，无需等待数据库IO
  2. 削峰填谷: 消息队列缓冲瞬时高并发流量，后台线程按能力消费
  3. 可靠性: Pending 机制保证消息不丢失，异常自动重试
  4. 原子性: Lua脚本保证库存扣减和用户判重的原子性

⚠️ 注意事项

  1. 库存预扣减: Lua脚本中已扣减Redis库存，消费者不再重复扣减
  2. 二次校验: 消费者仍需查询数据库做一人一单校验（防止Redis数据不一致）
  3. 线程池配置: 固定10个线程消费，可根据数据库承受能力调整
  4. ACK时机: 必须在业务成功后才ACK，否则会导致消息丢失
