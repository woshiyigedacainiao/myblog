一、秒杀下单优化：Lua 脚本合并 + 去除分布式锁

1.1 优化背景

在优化前，秒杀下单流程（doMiaosha）存在严重的性能瓶颈：每次请求需要多次 Redis 调用，并且使用 Redisson 分布式锁将所有用户对同一商品的请求串行化处理，导致并发能力极低。

存在的问题：

问题 影响
分布式锁将并发串行化 100 个用户抢 100 个库存，同一时刻只有 1 个用户能进入临界区，吞吐量极低
3 次独立 Redis 网络调用 hasOrdered + Lua + rollback（失败时），每次都有网络 RTT 开销
hasOrdered 与 Lua 之间存在时间窗口 虽然概率极低，但理论上两个请求可能在 hasOrdered 检查通过后同时进入锁等待，先后执行 Lua

1.3 优化思路

核心思想：Redis Lua 脚本本身具有原子性——Redis 单线程模型保证一个 Lua 脚本执行期间不会被其他命令插入。因此，如果把「重复检查 + 库存扣减 + 用户标记」三步操作合并到一个 Lua 脚本中，就天然具备原子性，不再需要分布式锁。

1.5 优化前后对比

指标 优化前 优化后 提升
Redis 调用次数 3 次（hasOrdered + Lua + 可能的 rollback） 1 次（Lua 原子完成） 减少 66%
并发模型 Redisson 分布式锁，所有用户串行等待 Redis 单线程原子处理，无锁竞争 本质性改变
网络往返 锁获取/释放 = 额外 2 次网络 RTT 0 次额外往返 减少 100%
代码复杂度 Lua 脚本 + Redisson 锁 + try-finally 一个 Lua 脚本调用 大幅简化
吞吐量预期 受限于锁竞争（QPS ≈ 数百） Redis 单线程原子处理（QPS ≈ 数万） 提升 5-10 倍

1.6 为什么可以安全地去掉分布式锁？

疑问 解答
没有锁，会不会超卖？ 不会。Redis 单线程模型保证 Lua 脚本原子执行，get → 判断 → decr 之间不会插入其他命令
没有锁，会不会重复下单？ 不会。sismember 和 sadd 在同一个 Lua 脚本内原子执行，检查和标记之间不会插入其他命令
分布式锁之前起什么作用？ 之前锁的作用是把「hasOrdered 检查」和「Lua 扣减」两步变成串行。现在合并为一步后，锁就失去了意义

2.6 优化前后对比

场景 优化前 优化后

三、两次优化的核心思想总结

优化项 核心思想 技术手段
秒杀下单 合并操作，减少临界区 Lua 脚本原子性合并三步操作，消除锁的需求
支付 互斥 + 兜底，双重防线 Redisson 锁保证互斥 + DB WHERE 条件保证原子性

关键经验：

  1. 能用原子操作就不用锁：Redis Lua 脚本天然原子，能合并操作就合并，避免锁带来的性能损耗和复杂性。
  2. 关键操作必须有兜底：分布式锁不是万能的（Redis 主从切换、网络分区都可能导致锁失效），数据库的 WHERE 条件更新是最终防线。
  3. 锁的粒度决定并发上限：lock:{goodsId} 让所有用户串行（秒杀场景不得不如此），lock:pay:{orderNo} 只让同一订单串行（不同订单互不影响）。设计锁时必须考虑粒度。
