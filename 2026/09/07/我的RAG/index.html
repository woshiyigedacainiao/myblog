第 0 章 小白必读：RAG 是什么

0.1 一句话解释

RAG（Retrieval-Augmented Generation，检索增强生成）：用户提问时，先从你自己的文档库里检索出相关资料，再把资料连同问题一起发给大模型，让大模型照着资料回答。

生活中的类比：

  • 不用 RAG = 学生闭卷考试，不会的题只能瞎编（这就是大模型的”幻觉”）。
  • 用了 RAG = 学生开卷考试，答案都在资料里，照抄整理即可。

0.2 RAG 的五个标准环节

环节 俗称 干什么 本项目对应代码
① Ingest 入库 读取文件 DocumentLoaderService
② Chunk 分块 把长文档切成小片段 DocumentSplitters.recursive(300, 50)
③ Embed 向量化 文字 → 一串数字（向量） ZeroDependencyEmbeddingModel
④ Retrieve 检索 拿问题向量去找最相似的片段 JsonFileEmbeddingStore.search()
⑤ Generate 生成 把资料+问题喂给大模型回答 chatModel.chat(chatRequest)

记忆口诀：入、切、嵌、检、生。

0.3 本项目相比”最简 RAG”多了什么

本系统不是教学级 Demo，而是带了 3 个生产级优化：

  1. Query Expansion（查询扩展，QE）：用户只问 1 句，先让大模型改写成 3 句同义问法，多路检索，防止”换个说法就搜不到”。
  2. HyDE（假设性文档扩展）：先让大模型”假装”写一段答案文档，用这段假答案去检索。因为假答案和真答案语气结构接近，更容易命中。
  3. 混合重排（Rerank）：检索结果不直接用，而是按 70% 向量语义分 + 30% 关键词重合分 重新排序，并过滤低分片段抗幻觉。

5.4.2 核心代码逐段讲解

说明：LangChain4j 的 EmbeddingModel 接口里，单文本 embed(String) / embed(TextSegment) 是 default 方法，内部会循环调用 embedAll，所以我们只实现 embedAll 即可。

关键思想讲解：

  • 为什么哈希可以当向量：语义相近的文本，分词后 token 集合重合度高，哈希后命中的维度就大量重合，向量方向自然接近。这是”词袋模型（Bag-of-Words）”的经典做法。
  • 为什么要 +1/-1 而不是全 +1：这叫 signed hashing。两个不相关的词万一哈希撞到同一维，符号相反可以互相抵消，降低碰撞带来的误差。
  • 为什么归一化：长文本 token 多、向量模长大，归一化后所有向量长度都是 1，此时两个向量的点积就等于余弦相似度，检索时直接算点积即可，又快又简单。

5.7.5 HyDE 假设文档

HyDE 为什么有效：用户问题通常是短句（”多少钱？”），文档答案是长陈述句（”XX平台单次部署39.8万元”），两者在向量空间里天然离得远。而 LLM 编的”假答案”也是陈述语气、包含同类关键词，和真答案在向量空间里非常近——用它当”检索探针”命中率更高。假答案内容不需要正确，只需要”长得像答案”。

5.7.6 中文分词与 Jaccard

为什么向量分之外还要加 Jaccard：向量检索懂同义改写但对精确词（数字、人名、产品名）不敏感；关键词匹配精确但不懂同义词。0.7×向量 + 0.3×关键词 两者互补。

ScoredSegment 内部类用来给每条候选挂上”粗召回名次/向量分/关键词分/综合分”四个字段，printRankingLog() 打印重排前后名次变化，方便调参观察。

第 6 章 关键算法原理

6.1 余弦相似度（检索的核心）

衡量两个向量”方向是否一致”：

  • 取值 [-1, 1]：1 方向完全相同，0 无关，-1 相反。
  • 本项目向量都做了 L2 归一化（|A|=|B|=1），所以公式直接简化为 点积 A·B，这正是 InMemoryEmbeddingStore 内部的计算方式。
  • LangChain4j 返回的 match.score() 是归一化到 [0,1] 的相似度分，越接近 1 越相似。

6.2 Jaccard 相似度（关键词重合）

两个 token 集合的交集除以并集。完全相同为 1，毫无共同词为 0。

6.3 特征哈希（Feature Hashing）

把任意多的词投影到固定 512 维空间：维度下标 = hash(token) % 512，配合 +1/-1 签名降低碰撞误差。优点：维度固定、无需维护词表、天然支持新词。缺点：有哈希碰撞、无语义理解。

6.4 L2 归一化

归一化后向量模长为 1，消除文本长度影响，点积即余弦。

6.5 递归分块（Recursive Splitting）

按分隔符优先级从大到小尝试切分：段落（\n\n）→ 换行（\n）→ 中文句读（。！？）→ 空格 → 字符。能在大分隔符切开就绝不在小分隔符切，最大化保持语义完整；超限时再用重叠窗口兜底。

6.6 Query Expansion 与 HyDE（检索增强两大论文级技巧）

技巧 一句话原理 解决的痛点
QE LLM 把问题改写成多种同义说法，多路召回 用户和文档用词不一致（”营收” vs “销售收入”）
HyDE LLM 先编一段”像答案的文档”，拿它去检索 问题是短句、答案是长陈述，向量空间距离远

两者都设计成失败非致命：异常时打 warn 日志并降级为原始单路检索，不影响主功能。

第 10 章 常见问题与踩坑 FAQ

Q1：启动报 ChatModel.chat() 编译错误 / 找不到 ChatRequest？
版本用错了。LangChain4j 0.x 旧 API 是 String chat(List<ChatMessage>)；1.x 新 API 是 ChatResponse chat(ChatRequest)。本项目是 1.0.0-beta2，必须用 ChatRequest/ChatResponse。pom 里版本号和代码写法要配套。

Q2：JDK 版本报错（invalid target release: 17）？
本机 JDK 低于 17。安装 JDK17，并在 IDEA 的 Project Structure 和 Maven Runner 里都切到 17。

Q3：调 DeepSeek 报 401 / AuthenticationFailed？
API Key 错误或欠费。检查 deepseek.api-key；用环境变量时确认 IDEA 运行配置里能读到 DEEPSEEK_API_KEY。

Q4：提问总是返回”根据现有资料，无法回答此问题”？
三种可能：① 还没加载文档（先调 /load）；② 阈值 0.30 太高或手写向量模型中文语义弱——可临时把 MIN_SCORE_THRESHOLD 调到 0.15 观察日志分数；③ 换用真正的神经网络 Embedding（MiniLM/BGE）。

Q5：重启后之前加载的文档还在吗？
在。data/vector_store.json 已落盘且 auto-load=true。若想”干净启动”，调一次 /clear 或删除该文件。

Q6：PDF 加载了但返回 0 个块？
扫描件 PDF 是图片没有文字层，Tika 解析为空。需要 OCR（如 Tesseract）先转文字。

Q7：批量加载大目录很慢？
当前 auto-save=true 是每加一块就刷一次盘。批量场景可把 rag.vector-store.auto-save 设为 false，加载完手动调 flushToDisk()（或依赖 @PreDestroy 关闭时刷盘）。

Q8：多次加载同一文件，向量重复了怎么办？
当前实现没有去重，重复加载会重复入库。生产做法是入库前用”文件路径+内容哈希”判重，或给 TextSegment 写入 metadata 后按 metadata 过滤。

Q9：embedding-model: deepseek-embedding 配了为什么不生效？
那是预留残留配置，没有代码读取它。当前 Embedding 是 ZeroDependencyEmbeddingModel。

Q10：中文乱码 / yaml 里注释显示成 ?????？
文件编码问题。IDEA 里把 application.yaml 另存为 UTF-8（Settings → Editor → File Encodings 全部设 UTF-8）。

第 11 章 已知不足与进阶方向

本项目为了”零依赖、可跑通、易学习”做了若干取舍，诚实记录如下：

# 现状 不足 进阶方向
1 手写词袋向量模型 不懂真正语义，”开心/高兴”无法匹配 换 MiniLM（离线）/ BGE-zh（中文强）/ DeepSeek 在线 Embedding
2 InMemory + JSON 文件存储 全量加载内存、无 ANN 索引，万级以上变慢 换 Milvus / Qdrant / PgVector 专业向量库
3 分块固定 300 字符 未按 Token 计数、未做父子分块 Token-based splitter、Parent-Child 分块
4 无文档去重 重复加载重复入库 内容哈希 + metadata 判重
5 metadata 的 documentName 未写入 RagService 读了 documentName 但入库时没塞 TextSegment.from(text, Metadata.from("documentName", 文件名))
6 无多轮对话记忆 每次问答独立 引入 ChatMemory（MessageWindowChatMemory）
7 同步阻塞返回 大模型等待时间长 SSE 流式输出（StreamingChatModel）
8 无答案质量评估 不知道检索/生成好不好 接 LangChain4j Eval（Faithfulness/Relevance 指标）
9 每次问答 3 次 LLM 调用 成本与延迟偏高 QE/HyDE 加缓存、按问题难度开关

结语：这套系统完整体现了 RAG 的”入、切、嵌、检、生”五大环节，并在检索侧叠加了 QE、HyDE、混合重排、阈值过滤、来源溯源五个生产级手段。把第 5 章每个类的逐行讲解吃透，再按第 9 章 Checklist 亲手重写一遍，你就真正掌握了 RAG 工程落地的主干脉络。后续优化（专业向量库、神经网络 Embedding、流式、记忆、评估）都可以在这套骨架上平滑替换。
