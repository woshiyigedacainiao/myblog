本地消息表实现详解

这是整个流程最核心的可靠性保障机制。

表结构（oms_local_message）

字段 说明

核心机制：事务内写消息 + 事务后发消息

解决的问题：如果先发 MQ 再写库，MQ 发成功但 DB 回滚，消费者收到消息却找不到订单；如果先写库再发 MQ，DB 提交后发 MQ 时网络闪断，消息就丢了。本地消息表让 消息和订单在同一事务内持久化，保证「订单在，消息就在」。

用到的技术及解决的问题

技术手段 解决的问题
本地消息表（oms_local_message） 解决「DB 事务与 MQ 发送的原子性」问题，保证消息至少投递一次
事务后发送（afterCommit） 避免消息先发但事务回滚导致的脏消息
Publisher Confirm + Return 回调 感知消息是否真正到达 broker，失败则标记待重试
定时补偿任务 + 指数退避 MQ 发送失败后的自动重投，避免消息永久丢失；退避防止 broker 压力过大
死信队列（DLX） 消费失败的消息集中留痕告警，避免无限重试阻塞队列
消费幂等日志（oms_consume_log，msg_id 唯一索引） MQ 重复投递时不会重复锁库存、重复改状态
Redis 预扣 + DB 锁库存两阶段 下单快速返回（Redis 扛量），DB 保证数据准确（最终一致性）
CAS 状态更新（WHERE status = from） 防止并发状态流转冲突（如同时支付和取消）
DB 条件扣库存（WHERE stock >= qty） 数据库层防超卖，Redis 挂了也不会卖超
超时订单取消任务 消息丢失/用户不付款时自动释放库存，避免库存长期占用
库存对账任务 定期修复 DB/Redis 偏差，保证最终一致

一句话总结

整个正常购物流程围绕 「最终一致性」 设计：用 本地消息表 保证 MQ 不丢，用 消费幂等 保证 MQ 不重，用 Redis 预扣+DB 锁定 两阶段保证库存准确，用 超时取消+对账任务 兜底异常场景。即使任何一个环节出问题，都有补偿机制把数据拉回一致状态。

完整执行链路如下：

第 ⑥ 步：Redis Lua 原子预扣（seckill_deduct.lua）

为什么用 Lua？ 因为 GET → 判断 → DECRBY 不是原子的，高并发下会超卖。Lua 脚本在 Redis 单线程中执行，保证整个判断+扣减是原子的。

第 ⑧ 步：DB 层二次扣减（SeckillTxServiceImpl.createSeckillOrder）

这是 第二道防超卖闸门。即使 Redis 出问题，DB 条件更新也不会让库存变负数。整个方法加了 @Transactional，扣库存 + 插订单 + 插订单项要么全成功要么全回滚。

异常回滚机制

如果第 ⑧ 步 DB 落库失败（抛异常），会调用 rollbackRedis() → seckill_return.lua 把刚才 Redis 预扣的库存和限购记录回补回去，保证 Redis 与 DB 一致。

三、结果查询阶段

SeckillOrderServiceImpl.result()：根据 activityId + userId 查最新订单，返回秒杀是否成功、订单号、状态、金额等。

四、订单取消回补阶段

OrderServiceImpl.restoreSeckillStock()：用户取消秒杀订单时，DB 库存回补 + Redis 库存与限购记录回补，双向保持一致。

技术手段 解决的问题
Redis + Lua 脚本 高并发下原子性扣库存，避免 GET-判断-DECRBY 的竞态导致超卖
Redis Hash（seckill:bought） 记录每个用户已购数量，解决超限购问题（一人只能买 N 件）
DB 条件更新（WHERE available_stock >= quantity） 第二道防超卖闸门，Redis 挂了也不会卖超
Spring @Transactional DB 扣库存 + 生成订单原子性，防止扣了库存没订单或有订单没扣库存
requestId 幂等校验 防止用户重复点击/网络重试导致重复下单
Redis 预扣 + DB 兜底 + 失败回补 解决高并发性能（Redis 扛流量）与数据一致性（DB 为准，失败回补 Redis）
TransactionSynchronization.afterCommit 事务提交成功后才发站内信，避免通知失败导致订单回滚
Redis Set（seckill:joined） 去重统计参与人数，用于后台转化率分析

一句话总结架构思路

Redis 扛流量（Lua 原子预扣+限购），DB 保数据（条件更新防超卖），事务保一致，幂等防重复，回补保闭环。

这是一个经典的「Redis 预扣 + DB 兜底」双保险秒杀方案，在保证不超卖、不超限购的前提下，用 Redis 承接了绝大部分高并发请求，DB 只处理真正抢到的少量订单。

踩过的坑（供参考）：

  • Spring 的 @Transactional 同类内部调用失效 → 拆独立 TxService Bean。
  • 事务没提交就发 MQ → 用 TransactionSynchronization.afterCommit。
  • Sa-Token 的 sa-token-redis-jackson 强依赖 Jackson 2，与 Spring Boot 4 内置的 Jackson 3 冲突启动报 NoClassDefFoundError → 换成不绑定 Jackson 版本的 sa-token-redis-template。

这套架构没有用任何”高大上”的组件，全部是 Spring Boot 生态最主流的技术，但把 缓存原子性、消息可靠性、数据库乐观并发 这三个分布式系统的核心问题在一个单体里完整落地了——这也是它适合作为技术博客和课程设计的原因：麻雀虽小，五脏俱全。

高并发下单 Redis预扣+MQ异步落库 架构完整复盘文档

一、基础业务流程

核心流程

用户下单 → Redis Lua 脚本校验库存 + 预扣库存

  1. Redis 库存不足：直接返回库存不足，下单失败

  2. Redis 预扣成功：发送 MQ 消息，消费者异步操作数据库，完成真实库存扣减、订单生成

架构核心目标

实现服务高可用，保证 Redis 缓存库存 与 DB 真实库存的最终数据一致性

二、架构核心风险点（六大核心问题）

该异步架构存在严重的数据不一致、服务异常风险，是整套方案重点解决的痛点：

  1. 库存泄露：Redis 预扣成功，服务突然宕机，MQ 消息未生成。最终 Redis 库存已扣减，但数据库无订单记录、真实库存未扣减，造成库存丢失。

  2. 消息丢失：MQ 消息丢失或消费者消费失败，数据库永久不扣减真实库存，Redis 预扣库存永久占用。

  3. 超卖问题：MQ 消息重复消费，导致数据库重复扣减库存，出现超卖。

  4. 库存锁死：Redis 预扣库存后，下游业务执行失败，未回滚 Redis 库存，导致库存永久锁定，用户无法正常下单。

  5. 服务不可用：Redis 宕机，整体下单链路直接瘫痪，无法承接请求。

  6. 超时库存占用：用户下单超时、放弃支付，预扣的临时库存未及时释放，导致库存资源浪费。

三、整体设计大原则

  1. 数据真值原则：数据库 DB 是库存唯一真值，Redis 仅作为临时预占缓存，不存储真实库存数据。

  2. 最终一致原则：Redis 所有库存数据，最终以数据库数据为准，支持全量重建、校正覆盖。

  3. 预扣回滚原则：Redis 临时预扣库存，若后续订单未正常落地，必须强制归还、释放库存。

四、分层完整解决方案

1. Redis 层：高可用 + Lua 原子预扣设计

（1）高可用部署规范

  • 禁止单机 Redis 部署，生产环境使用 Redis Cluster 集群 或 「主从 + 哨兵」架构，避免单点宕机导致下单服务瘫痪。

  • 开启 RDB+AOF 双重持久化，防止节点宕机导致内存预扣数据全部丢失。

（2）Lua 脚本原子性保障

2. 发送方链路：解决宕机丢消息、库存泄露

（1）错误流程（高危 Bug）

Redis Lua 预扣成功 → 直接发送 MQ

  • 风险：发送 MQ 前服务宕机，消息未生成，Redis 库存被扣、DB 无数据，造成永久库存泄露。

（2）标准正确流程

  1. Lua 脚本预扣库存成功；

  2. DB 事务兜底：同一事务中，插入「待确认订单记录」+「本地消息表（待发送状态）」，统一提交；

  3. 事务异常：数据库写入失败，立即执行 Lua 脚本回滚 Redis 库存，返回下单失败，不发送 MQ；

  4. 事务成功：提交后发送 MQ 消息，投递成功后更新本地消息表为「已发送」；

  5. 定时任务补偿：后台定时扫描本地消息表中「待发送」消息，自动重试投递，超过最大重试次数则标记失败并告警。

（3）MQ 投递辅助保障

  • RabbitMQ：开启 publisher-confirm 确认机制

  • Kafka：设置 acks=all

  • 注意：以上配置仅为辅助，无法替代本地消息表，不能单独保证消息可靠。

3. MQ Broker 层：高可用防丢失

  1. 集群多副本部署，消息开启持久化，Broker 重启不丢失消息；

  2. 配置死信队列 DLQ：多次消费失败的消息转入死信队列，人工排查，禁止无限重试阻塞业务队列；

  3. 实时监控：消息堆积、消费失败、消息延迟，异常立即告警；

  4. 边界说明：Broker 仅保证投递后的消息不丢失，无法解决业务未生成消息的宕机问题。

4. 消费方：幂等消费、防超卖、防丢失

消费者核心职责：异步消费消息，在数据库完成真实库存扣减、正式订单生成。

（1）核心配置

关闭 MQ 自动 ACK，全程使用手动 ACK机制：

  1. 接收消息，通过唯一 orderId 做幂等校验；

  2. 数据库执行业务：创建正式订单、扣减真实库存、更新订单状态；

  3. 业务执行成功，手动 ACK；执行异常，不 ACK，等待 MQ 重试。

（2）DB 级别强幂等（核心防超卖）

  • 订单表 orderId 设置唯一索引；

  • 重复消费时，插入订单会触发唯一索引冲突，直接 ACK 跳过，杜绝重复扣库存；

  • 禁止依赖 Redis 做幂等，Redis 宕机、清空会导致幂等失效。

（3）异常分类处理

  • 瞬时异常（网络抖动、DB 短暂宕机）：不 ACK，等待 MQ 自动重试；

  • 业务异常（商品下架、参数错误）：直接转入死信队列，告警人工处理。

（4）消息有序性

同一商品 ID 的消息路由至同一个 MQ 分区，避免消息乱序导致数据异常。

5. 两大兜底补偿机制（架构最后防线）

MQ 仅能处理「预扣成功、DB 已有记录」的场景，极端宕机场景必须依靠兜底任务。

兜底 1：预扣超时库存回收（解决库存锁死）

  • 场景：用户放弃下单、MQ 持续消费失败，待确认订单长期未完成，Redis 库存永久占用；

  • 方案：订单设置 30 分钟超时时间，定时任务扫描 DB 中待确认 + 已超时的订单；

  • 执行逻辑：修改订单为「已取消」，调用 Lua 脚本归还 Redis 预扣库存，释放资源。

兜底 2：全局库存数据校正（最高级别兜底）

  • 场景：极端宕机（预扣成功、未写入 DB 即宕机），库存泄露，超时任务无法识别；

  • 方案：每 5 分钟执行一次全局校正任务；

  • 执行逻辑：读取 DB 真实库存、Redis 缓存库存，数据比对；以 DB 真值为准，强制修正 Redis 库存，异常数据触发告警记录。

  6. 定时任务 A：扫描超时待确认订单，取消订单并归还 Redis 库存；

  7. 定时任务 B：全局比对 DB 与 Redis 库存，修复数据偏差、告警异常。

六、核心避坑清单

✅ 正确规范

  1. Redis 集群高可用 + Lua 原子预扣，区分缓存与真值；

  2. 预扣成功先落 DB、再发 MQ，异常必回滚缓存库存；

  3. MQ 集群持久化 + 死信队列 + 监控告警；

  4. 消费端手动 ACK + DB 唯一索引幂等，杜绝超卖；

  5. 超时回收任务，防止库存永久锁死；

  6. 全局数据校正，兜底所有极端异常。

❌ 致命错误

  1. 预扣成功直接发 MQ，无 DB 落地，宕机库存泄露；

  2. 消费端开启自动 ACK，DB 写入失败但消息已消费，数据丢失；

  3. 无幂等机制，重复消费导致库存超卖；

  4. 无超时归还逻辑，库存长期锁定；

  5. 将 Redis 缓存库存当作真实库存，无法修复数据错乱。

  3. 携带 Token 访问业务接口：Header 携带 Authorization: Bearer {token} → 网关 SaReactorFilter.checkLogin() 查 Redis 校验登录态 → 需要权限时回调 StpInterfaceImpl 从 Redis 读取角色权限（user:roles + role:permissions）→ AddUserId2HeaderFilter 用 Token 查 Redis 得到 userId 并注入请求头；
  4. 下游服务处理：服务 HeaderUserId2ContextFilter 将请求头中的 userId 存入 TTL ThreadLocal → 业务代码通过 LoginUserContextHolder.getUserId() 取用 → Feign 跨服务调用时 FeignRequestInterceptor 自动透传 userId 请求头；
  5. 异常与登出：未登录或权限不足由网关全局异常处理器统一返回 HTTP 401 与标准错误体；登出调用 StpUtil.logout(userId) 删除 Redis 会话，Token 立即失效。

方案要点回顾：

  • 网关统一鉴权，业务服务保持纯净，不引入安全框架；
  • 会话基于 Redis 集中存储，相比 JWT 支持服务端主动失效，auth 与 gateway 共享 Redis 完成会话共享；
  • 角色权限数据预热 + 用户角色注册时写入，网关鉴权全程只查 Redis，不打数据库；
  • userId 通过”请求头 + ThreadLocal + Feign 拦截器”在网关与微服务、微服务与微服务之间透传，形成完整身份链路。

一、项目背景与目标

1.1 项目背景

大语言模型（LLM，如通义千问、GPT）具备强大的自然语言理解与生成能力，但直接使用存在三个痛点：

  1. 知识盲区：大模型的训练数据有截止时间，对实时信息（如今天天气、近期新闻）和私有数据（如用户自己的 PDF 文档）无法准确回答；
  2. 幻觉问题：大模型会”一本正经地胡说八道”，在医疗、法律等严肃场景后果严重；
  3. 能力单一：纯对话无法完成查路线、查地图、操作文件等实际任务。

AIHub 项目就是为解决上述问题而生的 AI 助手后端平台，通过工程手段（RAG 检索增强、Function Calling 函数调用、知识图谱、MCP 协议等）把大模型的”通用对话能力”增强为”能查数据、能查文档、能调工具”的实用助手。

1.2 目标用户

  • 想学习 Spring Boot + AI 大模型应用开发的 Java 学习者；
  • 想把大模型落地到真实业务场景的开发者；
  • 面试中需要展示 AI 项目经验的求职者。

1.3 解决的核心问题 & 对应方案

痛点 解决方案 对应模块
大模型不知道实时信息 联网搜索（WebSearchTool） 通用对话模块
大模型回答长文本等待久 SSE 流式输出（Flux + TokenStream） 全部对话模块
大模型瞎编医疗答案 Neo4j 知识图谱 + Function Calling，答案严格来自图谱查询 医疗模块
大模型读不了私有文档 RAG：PDF 切分 → 向量化 → PgVector 相似度检索 PDF 模块
大模型不会查地图/路线 MCP 协议接入独立地图工具服务 出行模块
多轮对话重启丢失 自定义 ChatMemoryStore，对话记忆落库 MySQL 全部模块
用户身份识别 JWT 无状态认证 + ThreadLocal 传递用户上下文 用户模块

1.4 功能目标

  • 通用 AI 对话（支持联网搜索、流式输出、多轮记忆）；
  • 医疗知识问答（基于 Neo4j 图谱，防幻觉）；
  • PDF 文档智能问答（基于 RAG）；
  • 出行规划（基于 MCP 地图工具）；
  • 用户登录鉴权。

2.2 关键技术选型理由

为什么选 Spring Boot？

  • 约定优于配置：自动装配（AutoConfiguration）让你不用手写一堆 XML 配置，开箱即用；
  • 生态完整：Web、数据访问、安全、测试等 starter 一键引入；
  • 对比：传统 Spring MVC 需要大量 XML/注解配置，启动慢、学习曲线陡；Spring Boot 把这些都封装好了。

为什么选 LangChain4j 而不是直接调用大模型 API？

  • 直接调 API 需要自己写：请求封装、流式解析、对话历史管理、提示词拼接、函数调用编排；
  • LangChain4j 提供 AiServices 声明式接口（类似 Spring Data JPA，写个接口就有 AI 能力）、ChatMemory 对话记忆、@Tool 函数调用、RAG 检索器、MCP 客户端等高阶抽象；
  • 一句话：LangChain4j 是”Java 版的 LangChain”，把大模型应用开发从”手搓 HTTP”提升到”面向接口编程”。

为什么用 Neo4j 存医疗数据而不是 MySQL？

  • 医疗数据是”实体 + 关系”网络（疾病-症状-药品-食物），关系多跳且深度不定；
  • MySQL 多跳关系要多次 JOIN，表越大越慢；Neo4j 是原生图数据库，关系以”指针”存储，遍历只跟查到的节点数有关；
  • 查询语言 Cypher 直观，如：MATCH (d:Disease)-[:has_symptom]->(s:Symptom) WHERE s.name IN $symptoms RETURN d。

为什么用 PgVector 做向量检索？

  • 大模型的 RAG 需要”语义相似度”检索，传统 LIKE 是字面匹配做不到；
  • PgVector 是 PostgreSQL 的向量扩展，部署简单（装个扩展就行）、支持余弦/内积/欧氏距离、SQL 原生查询；
  • 对比 Milvus/Qdrant：PgVector 适合中小规模，无需额外维护一个向量数据库服务。

为什么用 JWT 而不是 Session？

  • JWT 无状态，服务端不存 Session，天然支持多实例部署、水平扩展；
  • 对比 Session：Session 需要服务端存储，分布式下还要共享（Redis），JWT 把状态放 Token 里，服务端只做验签。

八、常见问题与 Troubleshooting

8.1 环境搭建类

Q1：启动报错 Could not resolve placeholder 'ALI_API_KEY'

  • 原因：application.yml 中 ${ALI_API_KEY} 没有默认值，且环境变量未设置；LangChain4j DashScope 自动配置类在条件评估阶段就要解析该占位符。
  • 解决：① 设置环境变量 $env:ALI_API_KEY="sk-xxx"；② 或把 yml 改成 ${ALI_API_KEY:}（冒号后留空给默认值）。

Q2：启动报错 Communications link failure（连不上 MySQL）

  • 检查 MySQL 是否启动；
  • 检查 application.yml 中 url、username、password 是否正确；
  • 检查 MySQL 是否允许本地连接（bind-address）。

Q3：启动报错 Unable to connect to Neo4j

  • 检查 Neo4j 是否启动（http://localhost:7474 能否打开）；
  • 检查 spring.neo4j.authentication.password 是否为你设的密码；
  • 首次登录 Neo4j 浏览器会强制改密，改完要同步到 yml。

Q4：PDF 模块报错空指针（PgVector 连不上）

  • 原因：原 application.yml 的 dai.pdf 只配了 host 和 index-name，缺少 dataBase/table/port/user/password/dimension。
  • 解决：按本文 4.5 节补全 dai.pdf 下的全部字段。

8.2 运行时类

Q5：对话接口返回 401

  • 检查 Header 是否带 Authorization: <token>；
  • 检查 token 是否过期（默认 1 小时）；
  • 检查 JWT 密钥 dai.framework.jwt.base64-encoded-secret-key 是否被改动。

Q6：对话接口一直转圈不返回

  • 检查通义千问 API Key 是否有效、是否有余额；
  • 检查网络能否访问 DashScope API（国内可直连）；
  • 看日志是否有大模型调用超时。

Q7：医疗模块回答”未查询到相关信息”

  • 正常现象：说明工具查询图谱没匹配到。检查症状描述是否准确；
  • 可进 Neo4j 浏览器执行 MATCH (n:Disease) RETURN count(n) 确认图谱有数据；
  • 确认 build_medicalgraph.py 已成功执行。

Q8：出行模块报错（MCP 相关）

  • 检查 dai.api.mcp-server 路径是否指向真实存在的 Mcp-0.0.1-SNAPSHOT.jar；
  • 检查该 jar 能否独立运行（java -jar Mcp-0.0.1-SNAPSHOT.jar）；
  • 检查高德/百度地图 Key 是否配置。

Q9：ThreadLocal 用户串号

  • 确认 UserTokenIntercept.afterCompletion 中调用了 UserThreadLocal.removeSubject()；
  • 不要在异步线程（如 CompletableFuture）里读取 ThreadLocal（异步线程拿不到主线程的 ThreadLocal）。

8.3 性能优化建议

  1. MySQL 加索引：*_message 表的 memory_id、*_title 表的 user_id 建议加索引，否则数据量大后历史查询全表扫描；
  2. CompletableFuture 用自定义线程池：当前 runAsync() 用公共 ForkJoinPool.commonPool()，阻塞型落库任务可能拖慢其他功能，应传入自定义 ThreadPoolExecutor；
  3. 对话记忆压缩：滑动窗口 20 条仍可能超 token，可对历史消息做摘要压缩；
  4. PgVector 索引：向量数据量大后建 IVFFlat 或 HNSW 索引提升检索速度；
  5. OSS 上传加超时与重试：大文件上传建议分片上传。

8.4 安全注意事项

  1. 密钥绝不入库：API Key、数据库密码不要硬编码进代码或提交到 Git，用环境变量；
  2. JWT 密钥要够长：base64-encoded-secret-key 不要用弱密钥，定期轮换；
  3. JWT 不放敏感信息：payload 只 Base64 不加密，不要放密码；
  4. 文件上传校验：当前 PDF 上传只限制了大小（10MB），建议加文件类型白名单、病毒扫描；
  5. SQL 注入：项目所有查询用 #{} 预编译，安全；不要为了图快用 ${}；
  6. 生产环境关闭调试日志：application.yml 中 logging.level.org.springframework.data.neo4j=DEBUG 在生产应改为 INFO；
  7. HTTPS：生产环境必须用 HTTPS 传输 token。
